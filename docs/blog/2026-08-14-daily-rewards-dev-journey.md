# 一次完整的 AI 协作开发实录：从需求到上线的「晨光奖励系统」

> 朝词浅阅 · English Learning —— SRS 背单词 + 每日一读 + AI 学习日报
> 本文记录这个英语学习产品一次真实的功能迭代：**每日奖励系统**从想法到上线的全过程，以及背后一整套可复用的开发流程。

---

## 一、缘起：不只是功能，是"情绪价值"

「朝词浅阅」是一个英语学习产品：**SRS 背单词 + 每日一读 + AI 学习日报**，主打"每天进步一点点"的轻量学习体验。

产品本身已有打卡闭环：背词、阅读、手动打卡都会写入打卡记录，连续天数由算法实时推算。但当我们审视这个闭环时，发现一个关键缺口——

> **用户努力了，却没有"被看见"的反馈。**

打卡成功了，只是弹一句"打卡成功"；连续 30 天了，没有任何仪式感。学习是反人性的，而产品缺少给用户情绪价值的机制。

于是我们开始做**每日奖励系统**。这不仅是加一个积分功能，而是设计一套完整的激励闭环：

```
学习行为 → 积分到账 → 攒积分 → 兑换站 → 佩戴称号 → 继续学习
     ↑                                            │
     └──────────── 情绪价值贯穿始终 ────────────────┘
```

---

## 二、需求澄清：不急着写代码，先对齐"奖什么"

任何功能开发的第一原则：**先弄清楚用户要什么，再谈怎么实现**。我们按一次一个问题的方式，把需求逐层钉死：

| 问题 | 用户的选择 | 理由 |
|---|---|---|
| 奖励形式？ | **积分 + 兑换站**（而非纯徽章墙） | 积分可消耗、有收集感，闭环更明确 |
| 积分怎么获取？ | **每日任务制**（而非按量累计） | 有目标感，每天可拿约 40 分，节奏可控 |
| 情绪价值怎么体现？ | **温暖话语 + 每日晨语 + 里程碑庆祝 + 到账反馈**（全选） | 四个维度覆盖日常与仪式感 |
| 兑换站能换什么？ | **称号 + 装饰 + 彩蛋内容** | 身份感 + 个性化 + 回馈学习本身 |
| 数据存哪？ | **完整后端方案** | 跨设备同步，与账号体系一致 |

最有意思的环节是**称号命名**。第一版称号（"晨读人""词海舵手"）被用户一票否决：**"太老土了。"**

于是重做。我们尝试了"文人雅韵""晨光意象"两套方案，用户依然摇头，最后说出真正想要的风格：**玄幻**。最终定稿的六阶称号，既呼应产品气质，又自带修炼成长的隐喻：

> **聚灵（30分）→ 启明（60分）→ 蕴锋（100分）→ 承光（150分）→ 御风（220分）→ 观星（350分）**

每一档称号都是一层"境界"，攒积分就像修为精进——把英语学习包装成一段问道之旅。**好的设计藏在命名里。**

## 三、设计文档：把想法固化成 spec

需求对齐后，我们把设计写成一份正式的 spec 文档（`docs/superpowers/specs/`）。它回答了所有关键问题：

- **数据模型**：4 张新表——积分余额、积分流水、解锁记录、用户设置；流水表用 `(user_id, reason, ref_date)` 唯一约束天然防重复发放
- **任务分值**：打卡 +10 / 背词≥20 +10 / 读完 1 篇 +15 / 小测及格 +5
- **里程碑**：连续 7/30/100 天 → +50/+200/+800
- **兑换清单**：10 件道具的完整配置
- **结算机制**：学习行为完成后前端调 `collect()`，后端幂等结算
- **范围排除（YAGNI）**：不做排行榜、不做真实货币、彩蛋不做 LLM 生成

spec 的一个作用是**提前消灭歧义**。比如"里程碑只发一次"这句话，如果不写清"靠流水存在性判断"，实现时就会踩坑——后面真的踩了，详见第五节。

---

## 四、实施计划 + 子代理驱动开发：TDD 与双审查

设计批准后，我们把它拆成 **13 个可独立验收的任务**，从数据模型到前端集成逐步推进：

| 阶段 | 任务 |
|---|---|
| 数据层 | 数据模型（4 表）→ Alembic 迁移 → Repository 方法 → Pydantic Schemas |
| 业务层 | RewardService 核心逻辑（结算/里程碑/兑换/佩戴）→ API 路由 → 接口冒烟验证 |
| 前端 | 类型 + API 封装 + Pinia store → 4 个 UI 组件 → 页面集成 |
| 收尾 | 全量回归 → 终审 → 合并上线 |

每个任务采用**子代理驱动开发（Subagent-Driven Development）**：

```
派发实施子代理（读任务 brief，TDD 实现）
      │
      ▼
实施完成 → 生成 diff → 派审查子代理（spec 合规 + 代码质量）
      │
      ├── 通过 → 记录进度，进入下一任务
      └── 发现问题 → 派修复子代理 → 复审
```

关键实践：

1. **每个任务一个 brief**：brief 包含完整需求、精确代码、环境要点，实施子代理拿到就能干活，不依赖对话上下文
2. **TDD 贯穿**：先写失败测试 → 实现 → 测试转绿 → 提交，每任务独立 commit
3. **每任务双审查**：spec 合规（有没有多做少做）+ 代码质量（边界、幂等、风格）
4. **进度 ledger**：所有任务完成情况记录在 `.superpowers/sdd/progress.md`，防止上下文丢失后重复派发
5. **终审**：全分支合并前，派最有能力的审查员做最终质量门

这套流程最大的价值是**把质量关卡前置**。13 个任务里，审查一共揪出了 3 个真实 bug（详见下一节），如果直接闷头写，这些 bug 会进到生产环境才暴露。

---

## 五、真实案例：三个被审查揪出来的 Bug

**Bug 1 · 同日兑换两件道具必崩（Critical）**

兑换站里，同一天买称号再买装饰，第二次兑换直接抛数据库唯一约束异常——因为流水表的 `reason` 字段写死为 `"redeem"`，而唯一约束是 `(user_id, reason, ref_date)`。更糟的是，此时积分已经扣了。

修复：`reason` 改为 `f"redeem_{item_key}"`（按道具区分），并补了"同日兑换两件"的回归测试。

**Bug 2 · 称号永远无法兑换（UI 逻辑写反）**

兑换站称号子 Tab 里，未解锁的称号显示的是"已拥有"标签而不是兑换按钮——**用户永远买不到称号**。

修复：把"已拥有"分支换成兑换按钮。

**Bug 3 · 里程碑跨天重复发放（终审抓到的最大问题）**

这是最隐蔽的一个。幂等判断只查"**当天**该 reason 是否已有流水"，而里程碑的判断是 `连续天数 >= 7`。用户连续打卡 7 天后，**第 8 天、第 9 天……每天** `streak >= 7` 依然成立，但每天都是新日期 → **每天重复发 +50**。30 天里程碑每天 +200、100 天每天 +800，同理。

既有测试只验证了"同一天调用两次 collect 幂等"，恰好避开了跨天场景。终审时审查员指出：*"证据盲区——测试没覆盖真正的问题场景。"*

修复：新增 `has_point_log(user_id, reason)` 查询历史任意一天，并补了"模拟跨天后不重复发放"的测试。

> **启示**：幂等判断要问对问题——"今天发过吗"和"历史上发过吗"是两回事。这种 bug 单靠人肉代码审查很难发现，**靠的是流程**：终审这道门 + 审查员带着"设计意图 vs 实现"的核对清单。

## 六、上线与验证：CI/CD 自动部署

代码合并到 main 后，GitHub Actions 自动触发部署：

```
push main → 构建前端（VITE_BASE 指向子路径）→ 生成 SPA 404 回退 → 部署 GitHub Pages
```

整个产品线的部署是**纯静态前端**（GitHub Pages）+ **独立后端**（FastAPI + MySQL，本机/服务器运行）。前端每次 `git push` 约 1 分钟自动上线，无需人工干预。

上线验证包括：
- 接口层：curl 冒烟全部 5 个奖励接口，确认业务错误（积分不足）返回业务码而非 500
- 页面层：浏览器实际走完"打卡 → 积分到账 → 兑换 → 佩戴称号"全流程

## 七、方法论沉淀：这套流程还能复制到哪

回头看，这个项目的开发流程可以沉淀成一套通用方法论：

1. **需求澄清不跳步**：一次一个问题，多选优先，把模糊的"做一个奖励系统"变成可执行的 spec
2. **设计先行**：spec 里有数据模型、接口、验收标准、范围排除——实现前先消灭歧义
3. **任务拆解到"一任务一提交"**：每个任务独立可验收，失败可回溯
4. **子代理 + 双审查**：实施与审查分离，审查带"设计意图"核对，而不是走过场
5. **终审这道门不能省**：全分支合并前，用最严格的审查兜底
6. **回归测试补盲区**：审查员指出"测试没覆盖跨天场景"后，我们不仅修了 bug，还补了测试——**每个 bug 修复都要带回一个能拦住它的测试**

这套流程不只是"AI 开发"专用，**任何团队协作开发**都适用。子代理只是让"实施"变得更快更便宜，真正保证质量的是：**需求对齐 → 设计文档 → 任务拆分 → 独立审查 → 回归测试**这条流水线。

---

## 八、写在最后

一次奖励系统迭代，我们收获了：

- 一个完整的**用户闭环**：学习 → 积分 → 兑换 → 佩戴 → 继续学习
- 一个可复用的**开发流水线**：从需求到上线的全流程方法论
- 三个被流程拦截的**真实 bug**，其中一个是终审才暴露的跨天幂等漏洞

技术的乐趣不只是写代码，更在于**设计一套让代码质量可控的流程**。当"里程碑只发一次"这样的细节都能被流程兜住时，我们交付的不只是一个功能，而是一种确定性。
